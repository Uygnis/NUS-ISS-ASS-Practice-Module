[[topology]]
== Topology

*One MySQL 8.0 instance, five schemas.* Locally a Docker container; on AWS one
`db.t4g.micro` RDS instance. In MySQL, `SCHEMA` and `DATABASE` are synonyms, so
"five schemas" means five `CREATE DATABASE` statements.

[cols="2,1,4",options="header"]
|===
| Schema | Tables | Contents

| `rentez_auth`         | 6–8 | Users, roles, profiles, licences, tokens
| `rentez_fleet`        | 9   | Locations, vehicles, images, features, rates, maintenance
| `rentez_booking`      | 8–9 | Bookings, date reservations, handovers, extras, history
| `rentez_payment`      | 4   | Payments, refunds, gateway log, cancellation policy
| `rentez_notification` | 3   | Templates, notifications, preferences
| *DynamoDB*            | 3   | Sessions, availability projection, audit trail
| *Total*               | *30–33 MySQL + 3 DynamoDB* |
|===

The ranges are optional tables: `permissions` and `role_permissions` in
`rentez_auth` (see <<auth>>), and `report_snapshots` in `rentez_booking` (see
<<reporting>>). All three default to *omitted*.

=== No foreign keys cross a schema boundary

Within a schema, foreign keys are *mandatory* and declared with explicit
`ON DELETE RESTRICT`. Across schemas there are *none* — a booking row stores
`customer_id` and `vehicle_id` as plain identifiers, validated by an API call to
the owning service at write time.

This costs nothing on a single instance and buys two things: it makes the
service boundaries real rather than decorative, and it means any one service can
later be moved to its own database instance with no schema change at all. That
claim is the payoff, and <<cross-schema>> lists every link it depends on.

[[conventions]]
== Conventions that apply to every table

Read this section once. It is not repeated in the per-table definitions, where
"audit columns" and "soft-delete columns" refer back here.

=== Primary keys

[cols="3,4",options="header"]
|===
| Table type | Strategy

| Business entities exposed via the API +
  (users, vehicles, bookings, payments)
| `BIGINT UNSIGNED AUTO_INCREMENT` internal PK *plus* a
  `public_id CHAR(26) NOT NULL UNIQUE` ULID exposed externally

| Reference and lookup tables +
  (roles, categories, extras, locations)
| `INT UNSIGNED AUTO_INCREMENT` PK, plus a stable `code VARCHAR(32) UNIQUE`

| Join tables
| Composite PK on the two foreign keys
|===

The dual-key pattern is deliberate. A `BIGINT` PK keeps joins and index pages
small on a `t4g.micro`, which matters when Booking is under load test. A ULID
public identifier stops customers enumerating other people's bookings by
incrementing a URL, and ULIDs sort chronologically, which makes them pleasant in
logs.

WARNING: *Never expose the `BIGINT` id in an API response or a URL.* It leaks
row counts and invites enumeration.

=== Standard audit columns

Every business table carries all five. Reference tables carry the first two.

[source,sql]
----
created_at   DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at   DATETIME(3)      NOT NULL DEFAULT CURRENT_TIMESTAMP(3)
                              ON UPDATE CURRENT_TIMESTAMP(3),
created_by   BIGINT UNSIGNED  NULL,     -- users.id of the actor; NULL if system
updated_by   BIGINT UNSIGNED  NULL,
version      INT UNSIGNED     NOT NULL DEFAULT 0   -- JPA @Version
----

`version` is optimistic locking. It matters most on `bookings`, where two staff
members editing the same reservation must not silently overwrite each other.

=== Timestamps and time zone

All `DATETIME` columns store *UTC*. No exceptions.

[WARNING]
====
*Do not use MySQL `TIMESTAMP`.* It applies session time-zone conversion, so the
same row reads differently on a developer's laptop and on RDS — silently, and
usually discovered during a demo. Use `DATETIME(3)`.
====

`DATETIME(3)` (millisecond precision) rather than `DATETIME`, because booking
creation ordering under concurrent load needs sub-second resolution to mean
anything. Genuinely date-only values — a maintenance calendar day, an
availability day — use `DATE`.

The API accepts and returns ISO-8601 with an explicit offset; the React frontend
converts to the browser's zone for display.

=== Money

[source,sql]
----
amount    DECIMAL(12,2) NOT NULL,
currency  CHAR(3)       NOT NULL DEFAULT 'SGD'
----

[CAUTION]
====
*`FLOAT` and `DOUBLE` are prohibited for any monetary value.* Java-side use
`BigDecimal` with `RoundingMode.HALF_UP`, never `double`.
====

Every table holding an amount also holds its currency, even though the MVP is
SGD-only — adding the column later means backfilling every historical row.

*Tax.* Singapore GST is *9%*. It is stored on the booking as both a rate and an
amount:

[source,sql]
----
tax_rate_snapshot  DECIMAL(5,2)  NOT NULL DEFAULT 9.00,
tax_amount         DECIMAL(12,2) NOT NULL DEFAULT 0.00
----

That is not redundancy. If GST ever moves, a historical booking must still be
able to explain its own arithmetic; an amount without its rate is a number
nobody can reproduce. Rounding is `HALF_UP` to two decimals, applied once at the
tax line rather than per rental day.

=== Soft deletion

Rows that appear in historical records are never hard-deleted. US-16 ("remove
vehicles from the inventory") must not `DELETE` a vehicle that appears in a
completed booking.

[source,sql]
----
is_deleted  BOOLEAN         NOT NULL DEFAULT FALSE,
deleted_at  DATETIME(3)     NULL,
deleted_by  BIGINT UNSIGNED NULL
----

All read queries filter `is_deleted = FALSE`. Use a JPA `@Where` clause or a
Hibernate filter so that no developer can forget.

IMPORTANT: Unique constraints on soft-deletable tables *must include
`is_deleted`* — otherwise a registration number can never be reused after a
vehicle is retired. This is why `vehicles` has `UNIQUE (registration_number,
is_deleted)` rather than `UNIQUE (registration_number)`.

=== Enumerated values

Status and type columns use `VARCHAR(32)` with a `CHECK` constraint, *not*
MySQL's `ENUM` type. `ENUM` needs a DDL migration to add a value and orders
lexically in surprising ways.

Java-side, map with `@Enumerated(EnumType.STRING)` — *never* `ORDINAL`, which
corrupts data the moment somebody reorders the enum constants.

=== Correlation IDs

Every inbound request is assigned an `X-Correlation-Id` at the gateway,
propagated through every downstream call and every SQS message attribute, and
written into every log line and audit record. Tables that record events carry a
`correlation_id CHAR(36)`.

Without it, tracing one failed booking across five services during a load test
is guesswork.

== `rentez_auth` — Identity & Access (M1)

Owner: `account-service`. Six tables, plus two optional.

=== `users`

The identity record. Deliberately narrow, so the hot login query stays fast.

[cols="3,3,4",options="header"]
|===
| Column | Type | Notes

| `id`                    | BIGINT UNSIGNED PK | Internal
| `public_id`             | CHAR(26) UNIQUE    | ULID, exposed externally
| `email`                 | VARCHAR(255)       | Unique with `is_deleted`; store lowercased
| `password_hash`         | VARCHAR(72)        | BCrypt output, work factor 12
| `first_name`            | VARCHAR(100)       |
| `last_name`             | VARCHAR(100)       |
| `mobile_number`         | VARCHAR(20)        | E.164
| `role_id`               | INT UNSIGNED FK → `roles` |
| `status`                | VARCHAR(32)        | `PENDING_VERIFICATION`, `ACTIVE`, `SUSPENDED`, `LOCKED`, `DELETED`
| `email_verified`        | BOOLEAN            |
| `email_verified_at`     | DATETIME(3) NULL   |
| `failed_login_attempts` | TINYINT UNSIGNED   | Lockout counter
| `locked_until`          | DATETIME(3) NULL   |
| `last_login_at`         | DATETIME(3) NULL   |
| _soft-delete columns_   |                    | See <<conventions>>
| _audit columns_         |                    | See <<conventions>>
|===

Indexes: `UNIQUE (email, is_deleted)`, `UNIQUE (public_id)`,
`INDEX (role_id, status)`, `INDEX (status, created_at)`.

=== `roles`

`id`, `code` (`CUSTOMER` / `STAFF` / `ADMIN`, unique), `name`, `description`,
`created_at`, `updated_at`.

Role assignment is exclusive — a user holds exactly one role. `ADMIN` is a strict
superset of `STAFF` in every requirement in the PRDs.

=== `permissions` and `role_permissions` — optional, omit

With exactly three fixed roles, method-level
`@PreAuthorize("hasRole('ADMIN')")` is sufficient. These two tables cost a join
on every authorisation check.

TIP: *Recommendation: omit for the MVP* and note the extension point in the
final report. Configurable RBAC is a good thing to have designed and a poor use
of the remaining sprint budget.

=== `customer_profiles`

One-to-one with `users`, for customer-only attributes.

[cols="3,3,4",options="header"]
|===
| Column | Type | Notes

| `id`             | BIGINT UNSIGNED PK |
| `user_id`        | BIGINT UNSIGNED UNIQUE FK → `users` |
| `date_of_birth`  | DATE               | Drives the age ≥ 21 eligibility check
| `address_line1`  | VARCHAR(255)       |
| `address_line2`  | VARCHAR(255) NULL  |
| `city`           | VARCHAR(100)       |
| `postal_code`    | VARCHAR(20)        |
| `country`        | CHAR(2)            | ISO 3166-1 alpha-2
| _audit columns_  |                    |
|===

Splitting this from `users` keeps the authentication query narrow: login reads
`users` only and never touches address data.

=== `driving_licences`

[cols="3,3,4",options="header"]
|===
| Column | Type | Notes

| `id`                  | BIGINT UNSIGNED PK |
| `user_id`             | BIGINT UNSIGNED FK → `users` |
| `licence_number`      | VARCHAR(64)        | Encrypted at rest or masked in logs
| `issuing_country`     | CHAR(2)            |
| `issue_date`          | DATE               |
| `expiry_date`         | DATE               | Checked against the booking return date
| `licence_class`       | VARCHAR(16) NULL   |
| `image_s3_key`        | VARCHAR(512) NULL  | Object key only, never a public URL
| `verification_status` | VARCHAR(32)        | `PENDING`, `VERIFIED`, `REJECTED`, `EXPIRED`
| `verified_by`         | BIGINT UNSIGNED NULL |
| `verified_at`         | DATETIME(3) NULL   |
| `rejection_reason`    | VARCHAR(255) NULL  |
| _audit columns_       |                    |
|===

Indexes: `UNIQUE (user_id, licence_number)`, `INDEX (verification_status)`,
`INDEX (expiry_date)`.

Modelled as a table rather than columns on `customer_profiles` because a licence
can be resubmitted after rejection or renewal, and that history matters when a
dispute arises.

=== `password_reset_tokens` and `email_verification_tokens`

Identical shape: `id`, `user_id` FK, `token_hash` CHAR(64), `expires_at`,
`used_at` NULL, `requested_ip` VARCHAR(45), `created_at`.
`UNIQUE (token_hash)`, `INDEX (user_id, used_at)`.

IMPORTANT: `token_hash` stores the *SHA-256 of the token*. The raw token is
emailed and never stored, so a database leak cannot be used to reset anyone's
password.

Owner: `catalog-service`. Nine tables.

=== `locations`

`id`, `code` VARCHAR(16) UNIQUE, `name`, `address_line1`, `address_line2`,

=== `vehicle_images`

`id`, `vehicle_id` FK, `s3_key` VARCHAR(512), `content_type`,
`file_size_bytes`, `display_order` TINYINT, `is_primary` BOOLEAN, `alt_text`,
`uploaded_by`, `created_at`. Index `(vehicle_id, display_order)`.

Application rule: exactly one `is_primary = TRUE` per vehicle. MySQL cannot
express this as a constraint; enforce it in the service.

=== `features` and `vehicle_features`

`features` — `id`, `code` UNIQUE (`GPS`, `BLUETOOTH`, `REVERSE_CAMERA`,
`SUNROOF`, `CHILD_SEAT_ANCHOR`), `name`, `icon_name`, `display_order`.

`vehicle_features` — join table, composite PK `(vehicle_id, feature_id)`.

=== `rate_plans`

[cols="3,3,4",options="header"]
|===
| Column | Type | Notes

| `id`                  | BIGINT UNSIGNED PK |
| `category_id`         | INT UNSIGNED FK    |
| `name`                | VARCHAR(100)       | e.g. "Standard 2026", "Peak Season"
| `base_daily_rate`     | DECIMAL(10,2)      |
| `weekend_multiplier`  | DECIMAL(4,2) DEFAULT 1.00 | *Deferred — leave at 1.00*
| `weekly_rate`         | DECIMAL(10,2) NULL | *Deferred — leave NULL*
| `currency`            | CHAR(3)            |
| `effective_from`      | DATE               |
| `effective_to`        | DATE NULL          | NULL = open-ended
| `is_active`           | BOOLEAN            |
| _audit columns_       |                    |
|===

[WARNING]
====
Per ADR-001, `weekend_multiplier` stays at `1.00` and `weekly_rate` stays NULL
for the MVP. The columns exist so that enabling either later is a configuration
plus quote-calculation change rather than a migration.

*Do not write code that reads them until the team decides to enable them.* A
multiplier silently applied by half-finished logic is worse than no multiplier.
====

The non-overlap rule for effective dates must be enforced in application code —
MySQL has no exclusion constraint. Exactly one active plan must exist per
category for every date in the bookable window, or quotation fails.

`INDEX (status, expires_at)` for the expiry sweeper,
`INDEX (status, pickup_datetime)` for the no-show sweeper.

[NOTE]
====
*Why `vehicle_snapshot` is JSON and not a join.* A booking must stay readable
after a vehicle is retired and its row soft-deleted. Storing the
display-relevant attributes at booking time means a customer's 2024 rental
history still shows what they actually drove — without a join into a
soft-deleted row, and without cross-schema coupling.

The same reasoning drives `daily_rate_snapshot` and `tax_rate_snapshot`:
a booking must be able to explain its own total, forever.
====

[[reservations]]
=== `vehicle_date_reservations` — the double-booking guarantee

*The single most important table in the system.* Read <<double-booking>> before
writing any code that touches it.

[cols="3,3,4",options="header"]
|===
| Column | Type | Notes

| `vehicle_id`       | BIGINT UNSIGNED    | *Composite PK part 1*
| `reserved_date`    | DATE               | *Composite PK part 2*
| `reservation_type` | VARCHAR(16)        | `BOOKING`, `MAINTENANCE`, `BLOCKED`
| `booking_id`       | BIGINT UNSIGNED NULL FK → `bookings` | Set when type = `BOOKING`
| `maintenance_id`   | BIGINT UNSIGNED NULL | Cross-schema; set when type = `MAINTENANCE`
| `created_at`       | DATETIME(3)        |
|===

`PRIMARY KEY (vehicle_id, reserved_date)`. Indexes `(booking_id)` and
`(maintenance_id)` for cascade release, `(reservation_type, reserved_date)` for
utilisation reporting.

Exactly one of `booking_id` / `maintenance_id` is non-null, matching
`reservation_type`. Enforce with a `CHECK` constraint — MySQL 8.0 honours them.

One row per rental day: a booking from 10 to 12 August inserts three rows.
Bookings are stored *inclusive of both the pickup date and the return date*
(ADR-002), which RentEZ presents as a whole-day turnover buffer for cleaning
and inspection between rentals.

[cols="3,3,4",options="header"]

| Column | Type | Notes

| `booking_id`            | BIGINT UNSIGNED FK → `bookings` |
| `handover_type`         | VARCHAR(16)        | `PICKUP`, `RETURN`
| `performed_by`          | BIGINT UNSIGNED    | Staff user ID, cross-schema
| `performed_at`          | DATETIME(3)        |
| `location_id`           | INT UNSIGNED       | Where it physically happened

[[double-booking]]
=== The concurrency mechanism — read this before coding

The proposal names double bookings as the first problem RentEZ exists to solve,
and `booking-service` runs at up to ten pods. *Any solution relying on
application-level coordination is wrong by construction* — ten JVMs cannot see
each other's locks.

[cols="1,3,3",options="header"]
|===
| | Approach | Verdict

| A
| `SELECT` for overlapping bookings, then `INSERT` if none
| *Rejected.* Classic time-of-check-to-time-of-use race. Two pods both read "no conflict" and both insert. Fails under exactly the load the demo generates.

| B
| `SELECT … FOR UPDATE` on the vehicle row, then overlap check, then insert
| Correct, but serialises every booking for a vehicle behind one lock held across a cross-service quotation call. The contention shows up as latency and muddies the scaling evidence.

| C
| *Insert one row per rental day into `vehicle_date_reservations`; the composite primary key rejects any overlap*
| *Selected.*
|===

A booking for 10–12 August inserts `(42, 2026-08-10)`, `(42, 2026-08-11)`,
`(42, 2026-08-12)`. A concurrent booking for 11–13 August attempts
`(42, 2026-08-11)` and receives a duplicate-key error from InnoDB. The
transaction rolls back and the API returns `409`.

Correctness is delegated to the database's unique index — the one component all
ten pods share and the only one that is genuinely serialisable. There is no
application-level coordination at all, which is exactly why it scales.

.Implementation requirements — all seven are load-bearing
. The reservation inserts and the `bookings` insert occur in *one transaction*. A partial failure must leave nothing behind.
. Catch `DataIntegrityViolationException` and translate to `409 CONFLICT_VEHICLE_UNAVAILABLE`. *Do not pre-check then insert* — the pre-check is redundant and reintroduces the race.
. Insert dates in *ascending order* in every code path — creation, modification, and maintenance blocking alike. Two transactions inserting overlapping sets in opposite orders can deadlock; a consistent order makes one simply fail on the duplicate key.
. Cancellation, expiry and no-show delete the reservation rows in the *same transaction* as the status change. Maintenance cancellation and early completion release theirs the same way.
. Modification deletes the old range and inserts the new range in one transaction, so a failed modification leaves the original reservation intact.
. Set the InnoDB lock wait timeout to *5 seconds*, so a contended request fails fast rather than holding a pod thread during the load test.
. Maintenance windows write rows here too (ADR-002a). One table, one source of truth for "is this vehicle-day taken".

[TIP]
====
*This is the strongest technical content available for the final report.* A
concurrency guarantee that is provably correct under horizontal scaling,
achieved with a primary key rather than a distributed lock.

Run an explicit test — 50 JMeter threads booking the same vehicle for the same
dates — and report that exactly one succeeds.
====

[[reporting]]
== Reporting (M7) — no new tables

Every metric derives from tables that already exist.

[cols="3,4",options="header"]
|===
| Metric | Source

| Booking volume and status mix | `bookings.status`, `bookings.created_at`
| Revenue | `payments` where `status = CAPTURED`, minus `refunds` where `status = COMPLETED`
| Utilisation | `vehicle_date_reservations WHERE reservation_type = 'BOOKING'` ÷ (rentable vehicles × days)
| Vehicle downtime | `vehicle_date_reservations WHERE reservation_type = 'MAINTENANCE'`, cross-checked against `maintenance_records`
| Cancellation and no-show rates | `bookings.status`, `booking_status_history`
| Average duration and value | `bookings.rental_days`, `bookings.total_amount`
|===

`vehicle_date_reservations` doubles as the utilisation fact table — a pleasant
consequence of the double-booking design rather than a coincidence. Because
maintenance writes rows of its own, a single `GROUP BY reservation_type`
separates vehicle-days sold from vehicle-days lost to servicing.

*One optional table*, only if dashboard latency proves unacceptable:

`rentez_booking.report_snapshots` — `id`, `report_code`, `period_type`
(`DAILY` / `WEEKLY` / `MONTHLY`), `period_start` DATE, `period_end` DATE,
`metrics` JSON, `generated_at`, `generation_duration_ms`.
`UNIQUE (report_code, period_type, period_start)`.

[CAUTION]
====
*Do not build this pre-emptively.* Measure first. At 200 vehicles and a few
thousand bookings, live aggregation over indexed columns will be fast enough,
and a snapshot table introduces staleness that then has to be explained.

M7 is the only module that can damage the project without failing. A careless
full-table aggregation running during the load test will inflate booking
latency and contaminate the scaling evidence — the graph will show Booking
scaling to ten pods with latency rising anyway, and nobody will know why. Index
every report query, review the `EXPLAIN`, and give each endpoint a hard timeout.

== Migrations

Flyway, running on service startup. *One migration directory per schema*, owned
by the service that owns the schema. Files named `V<n>__<description>.sql`,
forward-only.

[source,properties]
----
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.enabled=true
spring.flyway.schemas=rentez_fleet
spring.flyway.locations=classpath:db/migration
----

[CAUTION]
====
*`ddl-auto=validate`, never `update`.* `validate` fails loudly when an entity
and the migrations have drifted apart, which is the feedback you want. `update`
silently mutates the database and hides the drift until production.

*Never edit an applied migration.* The checksum check will fail on every
teammate's laptop simultaneously. Write a new `V<n>__…sql`.

*Seed data is not a migration.* Migrations are schema and live in version
control forever; demo rows belong in `make seed`. Mixing them puts fake
customers in your production schema history.
====
