== What you are building

RentEZ is a microservice platform. Locally it runs as ten containers, but you
rarely need all ten at once — see <<modes>>.

[cols="2,1,4",options="header"]
|===
| Component | Port | Purpose

| Frontend (React + Vite)   | `3000` | The web application, with hot reload
| API gateway (nginx)       | `8080` | *Single entry point.* Mirrors the AWS ALB's path routing
| `account-service`         | `8081` | Identity and access — PRD module M1
| `reservation-service`     | `8082` | Booking — PRD module M3
| `catalog-service`         | `8083` | Fleet and vehicle catalogue — PRD module M2
| `notification-service`    | `8084` | Notifications — PRD module M5
| `payment-service`         | `8085` | Payment and refund — PRD module M4
| PostgreSQL 16             | `5432` | One instance, one database, five schemas
| Adminer                   | `8090` | Click-to-browse database UI
| DynamoDB Local            | `8000` | Sessions, availability projection, audit trail
|===

The service ports are unchanged from the existing `docker-compose.yml`, so
nothing you have already bookmarked breaks.

IMPORTANT: The frontend talks to the *gateway* on `8080`, never to a service
port directly. That is the same shape as production, where a single Application
Load Balancer routes by path. One `VITE_API_BASE_URL` value works in both
environments.

[[quickstart]]
== Five-minute start

Your first day, in five commands.

[source,bash]
----
git clone git@github.com:<org>/NUS-ISS-ASS-Practice-Module.git
cd NUS-ISS-ASS-Practice-Module

make check      # <1>
make up         # <2>
make seed       # <3>
make db-check   # <4>
----
<1> Verifies Docker, JDK 21, Maven and Node are installed and that Docker has
    enough memory. Creates `.env` from `.env.example` if it is missing.
<2> Builds and starts everything. First run pulls images and resolves Maven
    dependencies — allow ten minutes. Subsequent runs take under a minute.
<3> Loads demo vehicles, users and bookings.
<4> Confirms all five services can reach their own schema.

Then open http://localhost:3000.

.Expected output of `make db-check`
[source,text]
----
  SERVICE                PORT    STATUS   SCHEMA
  account-service        :8081   UP       rentez_auth
  reservation-service    :8082   UP       rentez_booking
  catalog-service        :8083   UP       rentez_fleet
  notification-service   :8084   UP       rentez_notification
  payment-service        :8085   UP       rentez_payment
----

All five should read `UP`. `UP` means the service reached its own schema;
`NO-DB` means it is running but exposes no datasource health component, and
`DOWN` means it is not responding at all — go to <<troubleshooting>>.

Follow it with `make db-isolation`, which tries to read `rentez_booking` as
`auth_user`. A `permission denied for schema` there is the *pass*: it is the
evidence that the service boundaries are enforced by PostgreSQL privileges
rather than by convention.

[[raw-compose]]
=== Without `make`

`make` is a thin wrapper — it exists so nobody has to memorise flags, not to
hide anything. Every target has a plain Docker Compose equivalent, and you will
need them if you are on Windows without WSL2, or if the `Makefile` is mid-edit.

[cols="2,3",options="header"]
|===
| Make target | Docker Compose equivalent

| `make up`
| `docker compose --profile app up -d --build`

| `make infra`
| `docker compose up -d`

| `make down`
| `docker compose --profile app down`

| `make clean`
| `docker compose --profile app down -v`

| `make logs S=catalog-service`
| `docker compose logs -f catalog-service`

| `make psql`
| `docker compose exec postgres psql -U postgres -d rentez`

| `make seed`
| `docker compose exec -T postgres psql -U postgres -d rentez -f - < db/seed/01-demo-data.sql`
|===

.Start everything — backend services, frontend, database and tooling
[source,bash]
----
docker compose --profile app up -d --build
docker compose ps                                    # <1>
docker compose logs -f                               # <2>
----
<1> Confirms which containers are running and which are healthy.
<2> All services at once. Add a service name to narrow it.

NOTE: The `app` profile is what separates the two modes. Services and the
frontend carry `profiles: ["app"]`, so a bare `docker compose up` starts only
the database, DynamoDB Local, Adminer and the gateway — Mode A. Adding
`--profile app` starts everything — Mode B. See <<modes>>.

[WARNING]
====
*Docker Desktop defaults to 2 GB of memory on some installations.* Five JVMs
plus Postgres under a 2 GB ceiling produces OOM kills with no useful error
message — containers simply vanish and the logs say nothing.

Set it in menu:Docker Desktop[Settings > Resources > Memory] to *8 GB* before
your first `make up`. `make check` warns you if it is too low.
====

Only someone deploying to AWS needs `aws`, `eksctl`, `kubectl`, `helm` and
`jq`. *Nobody needs an AWS account to write application code* — the local stack
has no cloud dependency whatsoever.

[[windows]]
=== On Windows

There is no separate Windows version of this project and there does not need to
be one. *Develop inside WSL2* and everything below works exactly as it does on
macOS — same `make` targets, same scripts, same output.

[source,powershell]
----
wsl --install -d Ubuntu
----

Then, inside the Ubuntu shell:

[source,bash]
----
sudo apt update && sudo apt install -y make openjdk-21-jdk
git clone <repo-url> ~/rentez && cd ~/rentez
make check
----

In menu:Docker Desktop[Settings > Resources > WSL Integration], enable your
Ubuntu distribution. Docker Desktop then serves the same daemon to both
Windows and WSL2, so there is nothing to install twice.

[IMPORTANT]
====
*Clone into the WSL filesystem (`~/rentez`), never into `/mnt/c/...`.*

`docker-compose.yml` bind-mounts `./frontend`, `./db/init` and
`scripts/gateway.conf` into containers. Bind mounts that cross the Windows
filesystem boundary go through a translation layer, and the effect is not
subtle: Vite's file watcher can take seconds to notice a save, and a Maven build
that takes 40 seconds in `~` can take several minutes under `/mnt/c`.

People usually conclude the project is slow rather than that the path is wrong.
====

==== What works without WSL2

If you cannot enable WSL2 — some managed laptops forbid it — you can still do
most things, with two gaps:

[cols="3,2,3",options="header"]
|===
| | Native Windows | Needs a shell

| The stack itself
| Yes — `docker compose` works from PowerShell. Use <<raw-compose>>, which maps
  every `make` target to its plain Compose equivalent
| —

| Building and testing services
| Yes — `mvnw.cmd` is committed alongside `mvnw`
| —

| `make`
| Not installed by default. `winget install ezwinports.make` if you want it
| —

| `scripts/smoke.sh` and everything in `aws/scripts/`
| No
| Git Bash runs them; WSL2 is better because `make` works too

| `aws`, `kubectl`, `helm`, `eksctl`
| Yes, all four ship native Windows builds
| —
|===

The honest summary: PowerShell alone gets you a running stack, but not the
end-to-end smoke test and not the AWS tooling. Git Bash closes the first gap.
WSL2 closes both and is the only option that gives every teammate an identical
environment, which is worth more than it sounds when a bug will not reproduce.

NOTE: A root `.gitattributes` forces LF line endings on every shell script, the
`Makefile`, the SQL and the YAML. Without it, Git for Windows' default
`core.autocrlf=true` checks those files out with CRLF and bash fails with
`$'\r': command not found` — an error that mentions neither Windows nor line
endings. If you hit it anyway, your clone predates that file: run
`git rm --cached -r . && git reset --hard` to re-checkout with the rules applied.

You will spend most of your time in *Mode A*.

[cols="1,3,3",options="header"]
|===
| | Mode A — infrastructure only | Mode B — everything in Docker

| Command
| `make infra`

| What runs in Docker
| Postgres, DynamoDB Local, Adminer, gateway

| Where services run
| From IntelliJ — btn:[Run] or btn:[Debug]
| Inside containers

| Breakpoints
| Yes, natively
| Only with remote-debug flags

| Memory
| ~400 MB
| ~2.5 GB

| Use it for
| *All backend development*
| Frontend work, integration testing, demos

Mode A works with no configuration because every datasource property defaults
to `localhost`:

[source,properties]
----
spring.datasource.url=jdbc:postgresql://${DB_HOST:localhost}:5432/rentez
----

Docker Compose overrides `DB_HOST=postgres`; your IDE uses the default. *One
properties file, both modes, no Spring profiles to remember.*

Note the URL names the *database*, `rentez`, and not a schema. Which of the five
schemas a service sees is decided by its role's `search_path`, set once in
`db/init/01-schemas.sql` — so every service shares one connection URL and only
`DB_USER` differs.

TIP: In IntelliJ, create one Run Configuration per service once, then use
menu:Run[Run... > Edit Configurations > Compound] to launch several at once.

== The database

=== One instance, five schemas

RentEZ uses *a single PostgreSQL 16 instance hosting five independent schemas* —
locally in Docker, and on AWS as one `db.t4g.micro` RDS instance. This matches
PRD §2.1 and costs the same as one schema, because RDS bills the instance, not
what is inside it.

[NOTE]
====
*This project used to run MySQL, and the port is worth understanding.* In MySQL,
`SCHEMA` and `DATABASE` are synonyms, so "five schemas" was five `CREATE
DATABASE` statements and each service's JDBC URL named its own. Postgres
separates the two: there is *one database, `rentez`*, holding *five schemas*
inside it, each owned by its own login role.

The schema is the better unit. A role cannot cross a schema boundary without an
explicit `GRANT`, but every service still shares one instance and one pool —
which is what keeps the connection arithmetic in the architecture doc tractable.
Two things also got simpler in the move: `payment` enforces "at most one
successful payment per booking" with a real partial unique index instead of the
`STORED` generated column MySQL needed to fake one, and `outbox_event.payload`
is `JSONB`.
====

[cols="2,2,2,2",options="header"]
|===
| Service | Schema | PRD module | Database user

| `account-service`      | `rentez_auth`         | M1 Identity & Access        | `auth_user`
| `catalog-service`      | `rentez_fleet`        | M2 Fleet & Catalogue        | `fleet_user`
| `reservation-service`  | `rentez_booking`      | M3 Booking                  | `booking_user`
| _not yet created_      | `rentez_payment`      | M4 Payment & Refund         | `payment_user`
| `notification-service` | `rentez_notification` | M5 Notification             | `notification_user`
|===

CAUTION: The repository service names differ from the PRD module names — the
PRD calls them `auth-service`, `vehicle-service`, `booking-service` and
`payment-service`. Use the mapping above rather than guessing, and note that
*`payment-service` does not exist in the repository yet*. Its schema is created
anyway so the service can be added later without touching database setup.

=== Why schemas rather than one shared database

Each service gets its own database *user*, granted privileges on its own schema
and nothing else.

[source,sql]
----
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, DROP, ALTER, INDEX, REFERENCES
  ON rentez_auth.* TO 'auth_user'@'%';
----

There is no `GRANT ... ON *.*` anywhere. `auth_user` running
`SELECT * FROM rentez_booking.bookings` receives a permission error, not a
result set.

[TIP]
====
*Screenshot that permission error.* It is the difference between _claiming_
service boundaries in the final report and _demonstrating_ them, and it takes
ten seconds to produce in Adminer.
====

Two rules keep the boundary honest:

. *No foreign keys across schemas.* A booking row stores `vehicle_id` as a
  plain identifier with no `REFERENCES` clause. Within a schema, foreign keys
  are mandatory.
. *Cross-service reads go through the owning service's API*, never through a
  direct query into another schema.

Follow both and PRD §2.1's claim holds: any one service could later be given
its own database instance with *no schema change* — only a connection string.

=== The initialisation script

`db/init/01-schemas.sql` creates all five roles, all five schemas and their
grants. It is idempotent, so re-running is harmless.

[source,sql]
----
-- rentez_startup_project_v1_1_20260810_1421SGT
-- One Postgres database, five schemas, five roles. Idempotent.
-- Abridged — see the file itself for the full commentary.

-- Postgres has no CREATE ROLE ... IF NOT EXISTS, hence the DO block.
DO $$ BEGIN
    CREATE ROLE auth_user LOGIN PASSWORD 'auth_pw';
EXCEPTION WHEN duplicate_object THEN RAISE NOTICE 'role auth_user already exists';
END $$;
-- ... and the same for fleet_user, booking_user, payment_user, notification_user.

-- AUTHORIZATION makes the role the schema OWNER, which is what lets Flyway run
-- DDL as that role with no further GRANTs. It is also what denies everyone
-- else: a non-owner has no USAGE on the schema unless it is granted, and
-- nothing here grants it. That omission IS the service boundary.
CREATE SCHEMA IF NOT EXISTS rentez_auth         AUTHORIZATION auth_user;
CREATE SCHEMA IF NOT EXISTS rentez_fleet        AUTHORIZATION fleet_user;
CREATE SCHEMA IF NOT EXISTS rentez_booking      AUTHORIZATION booking_user;
CREATE SCHEMA IF NOT EXISTS rentez_payment      AUTHORIZATION payment_user;
CREATE SCHEMA IF NOT EXISTS rentez_notification AUTHORIZATION notification_user;

-- So an unqualified CREATE TABLE from Flyway lands in the right schema, and an
-- unqualified SELECT from Hibernate finds it again. This is what lets
-- spring.flyway.schemas stay unset in every application.properties.
ALTER ROLE auth_user         SET search_path = rentez_auth;
ALTER ROLE fleet_user        SET search_path = rentez_fleet;
ALTER ROLE booking_user      SET search_path = rentez_booking;
ALTER ROLE payment_user      SET search_path = rentez_payment;
ALTER ROLE notification_user SET search_path = rentez_notification;

-- Postgres grants CONNECT to PUBLIC by default. Revoking and granting back
-- explicitly means the list of who can reach this database is exactly this list.
REVOKE ALL ON DATABASE rentez FROM PUBLIC;
GRANT CONNECT ON DATABASE rentez
  TO auth_user, fleet_user, booking_user, payment_user, notification_user;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
----

Docker mounts this into `/docker-entrypoint-initdb.d/`, where Postgres runs it
*once*, on first boot of an empty data volume.

[IMPORTANT]
====
Editing `01-schemas.sql` after the volume exists has *no effect* — Postgres only
runs the directory on an empty data directory. To re-apply it:

[source,bash]
----
make clean && make up
----

That deletes the database volume and starts fresh.
====

On AWS the same script runs as a one-shot Kubernetes Job, because RDS sits
inside the VPC and cannot be reached from a laptop. Same file, both
environments.

=== The NoSQL side

Three DynamoDB tables run locally in DynamoDB Local — AWS's own emulator, so
application code uses the unmodified AWS SDK and only the endpoint changes.

[cols="2,2,4",options="header"]
|===
| Table | Owner | Purpose

| `rentez-sessions`     | M1 | JWT sessions keyed on `jti`, self-expiring via TTL
| `rentez-availability` | M2 | 90-day read projection. *A cache, never a source of truth*
| `rentez-audit`        | M6 | Append-only audit trail, written by a shared library
|===

WARNING: `rentez-availability` must never be used to accept a booking. The
authoritative answer lives in `reservation-service`. It is a CQRS read model
and is eventually consistent — worth stating explicitly in the final report.

== Configuration and secrets

Configuration comes from `.env`, which is git-ignored. Copy the template once:

[source,bash]
----
cp .env.example .env
----

.`.env.example`
[source,properties]
----
# rentez_startup_project_v1_1_20260810_1421SGT
# Local development only. Nothing here is a real credential.

POSTGRES_PASSWORD=rentez
POSTGRES_DB=rentez
POSTGRES_PORT=5432
DB_PORT=5432

AUTH_DB_PASSWORD=auth_pw
FLEET_DB_PASSWORD=fleet_pw
BOOKING_DB_PASSWORD=booking_pw
PAYMENT_DB_PASSWORD=payment_pw
NOTIFICATION_DB_PASSWORD=notification_pw

# Fake AWS credentials — DynamoDB Local does not validate them.
# Never put real AWS keys in this file.
AWS_REGION=ap-southeast-1
AWS_ACCESS_KEY_ID=local
AWS_SECRET_ACCESS_KEY=localsecret
RENTEZ_AWS_DYNAMODB_ENDPOINT=http://localhost:8000

# HS256 requires at least 32 bytes. Regenerate: openssl rand -base64 48
RENTEZ_JWT_SECRET=local-dev-secret-change-me-min-32-chars
----

[CAUTION]
====
*Never commit `.env`.* The root `.gitignore` already excludes it (and
`.env.*`) while explicitly permitting `.env.example`. Do not weaken those
rules.

On AWS, none of these values exist in files — they are read from AWS Secrets
Manager at deploy time.
====

The `${VAR:default}` pattern in `application.properties` is deliberate: *the
defaults are the IntelliJ values*, so Mode A needs no configuration at all.

== Checking your database connection

Four independent ways, because different people reach for different tools.

=== Adminer — the visual one

Open http://localhost:8090 and sign in:

[cols="1,3",options="header"]
|===
| Field | Value

| System   | PostgreSQL
| Server   | `postgres` (or `localhost` if you started only `make infra`)
| Username | `auth_user`, `fleet_user`, `booking_user` …
| Password | from `.env`
| Database | `rentez` — then pick the matching schema in the left-hand pane
|===

Log in as one service's role and try to browse another's schema. It will not
appear. That is the isolation working.

=== `make db-check` — the fast one

[source,bash]
----
make db-check
----

Curls every service's health endpoint and prints one line each. This is the
command to run before asking anyone for help.

[[actuator-health]]
=== Actuator — the detailed one

[source,bash]
----
curl -s http://localhost:8083/actuator/health | jq .components.db
----

[source,json]
----
{
  "status": "UP",
  "details": { "database": "PostgreSQL", "validationQuery": "isValid()" }
}
----

This requires the following in every `application.properties` — without it only
a bare `/actuator/health` exists and the `db` component is hidden:

[source,properties]
----
management.endpoint.health.probes.enabled=true
management.endpoints.web.exposure.include=health,info,metrics
management.endpoint.health.show-details=when_authorized
----

[IMPORTANT]
====
`probes.enabled=true` is *not optional*. Kubernetes readiness and liveness
probes on AWS target `/actuator/health/readiness` and
`/actuator/health/liveness`. Without this property both return 404, every pod
fails readiness, never joins the load balancer, and the deployment appears to
hang for no visible reason.
====

=== The psql client — the definitive one

[source,bash]
----
docker compose exec -e PGPASSWORD=fleet_pw postgres \
  psql -U fleet_user -d rentez -c "\\dt"
----

`\dt` lists the tables on the role's `search_path`, so only `rentez_fleet`'s
tables appear. Reaching across the boundary is the more useful demonstration,
and `make db-isolation` runs it for you:

[source,bash]
----
docker compose exec -e PGPASSWORD=auth_pw postgres \
  psql -U auth_user -d rentez -c "SELECT COUNT(*) FROM rentez_booking.booking;"
# ERROR:  permission denied for schema rentez_booking
----

== Running the tests

[source,bash]
----
make test                                  # everything
cd services/catalog-service && ./mvnw test # one service
cd frontend && npm test                    # frontend
----

Three tiers, roughly in the proportion you should write them:

[cols="1,2,1,3",options="header"]
|===
| Tier | Tool | Speed | Use for

| Unit        | Plain JUnit, no Spring context   | ms    | Business logic, validation, price calculation
| Slice       | `@DataJpaTest` + Testcontainers  | ~2 s  | Repositories, queries, migrations
| Integration | `@SpringBootTest` + Testcontainers | ~10 s | Controllers end to end, wiring
|===

Tests get a *real PostgreSQL* from Testcontainers, not H2:

[source,java]
----
@SpringBootTest
@Testcontainers
class CatalogServiceApplicationTests {

    @Container
    @ServiceConnection                       // <1>
    static PostgreSQLContainer db = new PostgreSQLContainer("postgres:16-alpine");

    @Test
    void contextLoads() { }
}
----
<1> `@ServiceConnection` wires `spring.datasource.*` from the container
    automatically. No `@DynamicPropertySource`, no property juggling.

[WARNING]
====
*Do not use H2, even in "PostgreSQL compatibility mode".* It diverges from real
Postgres on exactly the things this project uses — `JSONB` columns, partial
unique indexes, identity columns, `CHECK` constraints. Tests that pass against
H2 and fail against RDS are worse than no tests. This codebase has already paid
for that lesson once: `car.model_year` is named that way only because `year` is
reserved in H2.

Testcontainers costs about 40 seconds on first run, then caches. Docker must be
running — it is available on GitHub's `ubuntu-latest` runners too.
====

Do not start a Spring context to test a pure function. If `contextLoads()`
remains the only test in a service, `./mvnw verify` is a slow way of proving
nothing.

  `spring.datasource.*` for `rentez_auth` / `rentez_notification`) when M1 and
  M5 work begins.

| 3
| *No Flyway, and no migrations.* `ddl-auto=none`, so the schemas exist but
  contain no tables.
| Add `flyway-core` and `flyway-mysql` in the same commit as the first
  `V1__init.sql`. See `docs/ch02.database-schema.adoc`.

| 4
| *`Dockerfile.dev` still uses `node:20-alpine` for the frontend while CI uses
  Node 22*, and Node 20 reached end of life on 30 April 2026.
| Pin `node:22-alpine`.

| 5
| *No Testcontainers.* `./mvnw verify` runs `@SpringBootTest` with no database
  on the CI runner, which will fail once entities exist.
| Add `org.testcontainers:mysql` and `spring-boot-testcontainers`, and use
  `@ServiceConnection`.
|===

CAUTION: A *Maven cache volume in `docker-compose.yml` would do nothing* — an
earlier version of this chapter suggested one. `mvn package` runs at image
*build* time and compose volumes exist only at *run* time. The dependency
layer above is the fix; a BuildKit cache mount
(`RUN --mount=type=cache,target=/root/.m2 …`) is the alternative.

[[troubleshooting]]
== Troubleshooting

[qanda]
`make up` hangs at "waiting for services"::
Docker needs 8 GB. Check menu:Docker Desktop[Settings > Resources]. Then
`make logs S=<service>` — the real error is almost always visible there.

`Failed to determine a suitable driver class`::
The service has JPA on the classpath but no datasource. This should not happen
in `catalog-service` or `reservation-service` — both are configured. If you see
it in `account-service` or `notification-service`, you have uncommented JPA
without adding the driver and `spring.datasource.*`.

`Access denied for user 'fleet_user'@'…'`::
The init script did not run, because the data volume already existed when you
added it. Run `make clean && make up`.

`Unknown database 'rentez_fleet'`::
Same cause as above. `make clean && make up`.

`Communications link failure` from IntelliJ::
You are in Mode A but the database is not running. `make infra` first. Confirm
with `docker compose ps`.

Actuator returns 404 on `/actuator/health/readiness`::
`management.endpoint.health.probes.enabled=true` is missing. See
<<actuator-health>>.

Testcontainers fails with "Could not find a valid Docker environment"::
Docker Desktop is not running. On Colima, export
`DOCKER_HOST=unix://$HOME/.colima/default/docker.sock`.

Port already allocated::
Something else holds the port — often a previously started stack.
`docker compose down` then retry, or `lsof -i :5432` to find the culprit. Every
host-side port is overridable in `.env` — set `POSTGRES_PORT=5433` and
`DB_PORT=5433` together, so Mode A in IntelliJ follows the move.

Frontend loads but every API call fails::
API calls are *relative* — the app requests `/api/…` with no host, and Vite's
dev-server proxy forwards them to the gateway. Check the gateway container is
healthy, and see the note in `frontend/vite.config.js` for why the production
build has no base URL baked into it either.

== Conventions worth knowing on day one

* *Flyway owns the schema.* `spring.jpa.hibernate.ddl-auto=validate`, never
  `update`. `validate` fails loudly when an entity and the migrations have
  drifted; `update` silently mutates the database and hides the drift until
  production.
* *Never edit an applied migration.* The checksum check will fail on every
  teammate's laptop simultaneously. Write a new `V<n>__…sql`.
* *Seed data is not a migration.* Migrations are schema and live in version
  control forever; seed data is throwaway demo content and belongs in
  `make seed`. Mixing them puts fake customers in your production schema
  history.
* *Never expose an internal `BIGINT` primary key* in an API response or URL.
  Public identifiers are ULIDs — see PRD §2.2.
* *Cap the connection pool.* `spring.datasource.hikari.maximum-pool-size=3`.
  On AWS, `db.t4g.micro` running Postgres allows roughly 112 connections
  (`max_connections` is `LEAST(DBInstanceClassMemory/9531392, 5000)`), three of
  them reserved for superusers. Twenty-five pods at full scale-out with a pool
  of 5 want 125 and would exhaust it at exactly the moment the autoscaler starts
  working — the load test would look like a scaling failure when it is a
  configuration failure. A pool of 3 wants 75, comfortably inside.
  +
  Note the local Postgres container is started with `max_connections=200`, which
  is deliberately *more* than RDS allows, so this failure cannot reproduce on
  your laptop.
